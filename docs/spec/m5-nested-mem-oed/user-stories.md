## エピック1: nested sampling 裁定

### ストーリー 1.1: 僅差競合だけを nested で厳密裁定 🔵
**信頼性**: 🔵 *FR-122/§14 リスク表*

**私は** 計算コストと裁定精度を両立したい研究者 **として**
**木探索は軽い bic で回し、evidence が僅差の上位仮説だけを nested sampling で厳密に裁定してほしい**
**そうすることで** nested の高コストを本当に判別が要る競合だけに集中でき、探索が破綻しない

**関連要件**: REQ-010, REQ-011, REQ-012, REQ-013, REQ-102, REQ-201 / **優先度**: Must Have

### ストーリー 1.2: logZ と誤差で確からしさを知る 🔵
**信頼性**: 🔵 *FR-121/FR-124/NFR-102*

**私は** 仮説選択の根拠を定量的に示したい研究者 **として**
**nested から logZ とその誤差を受け取り、サンプラー種を固定して再現可能にしてほしい**
**そうすることで** 「どちらの仮説がどれだけ確からしいか」を誤差付きで報告でき、再現性も担保できる

**関連要件**: REQ-006, REQ-007, REQ-009, REQ-402, EDGE-014 / **優先度**: Must Have

### ストーリー 1.3: 時間上限で暴走しない 🔵
**信頼性**: 🔵 *NFR-103/§14 リスク表*

**私は** 無人運転させる運用者 **として**
**nested が 1 仮説 30 分を超えたら打ち切って Laplace 代替へ落とし、警告を出してほしい**
**そうすることで** nested の計算コスト暴走で解析全体が止まるのを防げる

**関連要件**: REQ-001, REQ-002, REQ-101, REQ-405, EDGE-002, EDGE-005 / **優先度**: Must Have

### ストーリー 1.4: 外部サンプラが無くても壊れない 🔵
**信頼性**: 🔵 *CLAUDE.md optional extra*

**私は** dynesty/UltraNest を入れていない環境の利用者 **として**
**nested 実行だけが明示エラーになり、コア import と bic/laplace は普通に動いてほしい**
**そうすることで** 外部依存なしでコア解析を回し、必要になったら段階的に nested を導入できる

**関連要件**: REQ-004, REQ-005, REQ-403, EDGE-001 / **優先度**: Must Have

### ストーリー 1.5: 事前分布を restraint から自動で組む 🔵
**信頼性**: 🔵 *FR-125/§15-5*

**私は** 事前分布設計の負担を減らしたい研究者 **として**
**nested の事前分布を精密化 restraint(格子シフト上限・占有率拘束)から自動構成し、必要なら手動上書きしたい**
**そうすることで** 物理的に妥当な事前分布を手作業なしで得つつ、特殊ケースでは自分で指定できる

**関連要件**: REQ-008, REQ-301 / **優先度**: Should Have

## エピック2: MEM(Dysnomia 連携)電子/核密度解析

### ストーリー 2.1: 精密化結果から密度マップを得る 🔵
**信頼性**: 🔵 *FR-601/FR-604*

**私は** 伝導経路や結合電子密度を可視化したい研究者 **として**
**精密化済み仮説の F_obs から MEM 入力を自動生成し、X線なら電子密度・中性子なら核密度マップを出力してほしい**
**そうすることで** VESTA で開ける密度マップを手作業のファイル整形なしで得られる

**関連要件**: REQ-018, REQ-019, REQ-021, REQ-022, REQ-023, REQ-027 / **優先度**: Must Have

### ストーリー 2.2: 伝導パスの最小密度を測る 🔵
**信頼性**: 🔵 *FR-604*

**私は** Na/K イオン伝導体を評価する研究者 **として**
**指定したサイト間の結合経路に沿った 1D/2D 断面と、ボンド経路の最小密度値を出してほしい**
**そうすることで** 伝導パスのボトルネック(最小密度)を定量的に比較できる

**関連要件**: REQ-028, REQ-029 / **優先度**: Must Have

### ストーリー 2.3: MEM-Rietveld 反復を安全に回す 🔵
**信頼性**: 🔵 *FR-603/P2*

**私は** MPF 法で密度と構造を交互精密化したい研究者 **として**
**MEM 密度 → F_calc 更新 → 再精密化のサイクルを既定オフで、回すなら各サイクルを子スナップショットに残してほしい**
**そうすることで** 反復のどの段階にも revert でき、元の精密化結果を壊さずに MPF を試せる

**関連要件**: REQ-024, REQ-025, REQ-026, REQ-107, REQ-202, EDGE-008, EDGE-009 / **優先度**: Should Have

### ストーリー 2.4: 適用ガードは警告だけ、除外しない 🔵
**信頼性**: 🔵 *FR-605/P1 Dara 教訓*

**私は** 多相・低統計データにも MEM を試したい研究者 **として**
**推奨条件(joint 済み単相/主相支配)を外れたら信頼性警告は出しても、MEM 実行自体は止めないでほしい**
**そうすることで** ガードの助言を受けつつ、自己責任で境界的なデータにも MEM を適用できる(Dara の除外思想を避ける)

**関連要件**: REQ-030, REQ-031, REQ-103, EDGE-007 / **優先度**: Must Have

### ストーリー 2.5: 充放電端のスポット解析 🔵
**信頼性**: 🔵 *FR-606*

**私は** operando の特定状態の密度を見たい研究者 **として**
**シーケンシャル解析の充電端・放電端・転移前後の指定フレームだけに MEM をスポット実行したい**
**そうすることで** 全フレームを回さずに、注目状態の密度変化だけを効率よく解析できる

**関連要件**: REQ-032, REQ-405 / **優先度**: Should Have

### ストーリー 2.6: MEM は将来接続、受け口は M4 から 🔵
**信頼性**: 🔵 *FR-513/FR-602*

**私は** M4 の MCP クライアントをそのまま使いたい開発者 **として**
**M4 で用意した run_mem 受け口を MEMBackend へ実体化し、Dysnomia 未導入なら明示エラーに縮退してほしい**
**そうすることで** MCP クライアント側の接続を変えずに MEM が使えるようになり、未導入環境でも安全に返る

**関連要件**: REQ-020, REQ-033, REQ-034, REQ-104, EDGE-006, EDGE-013 / **優先度**: Must Have

## エピック3: OED / 測定フィードバック

### ストーリー 3.1: 僅差なら次の測定を提案してほしい 🔵
**信頼性**: 🔵 *FR-431*

**私は** 曖昧な結果を次の測定で解消したい研究者 **として**
**仮説が僅差で決まらないとき、高統計再測定・追加温度点・中性子測定・組成分析を情報利得順に提案してほしい**
**そうすることで** どの追加測定が最も判別に効くかを、根拠付きで知って計画できる

**関連要件**: REQ-035, REQ-038, REQ-304, EDGE-010 / **優先度**: Must Have

### ストーリー 3.2: 提案は非破壊、実行は人が決める 🔵
**信頼性**: 🔵 *FR-432/P2*

**私は** 自動化に任せつつ主導権は保ちたい研究者 **として**
**OED 提案は ledger に記録するだけで状態を変えず、v1 は提案生成に留めてほしい**
**そうすることで** 提案を監査可能な形で残しつつ、実際の測定実行は人間の判断で行える

**関連要件**: REQ-036, REQ-037, REQ-105, REQ-203, EDGE-011 / **優先度**: Must Have

## エピック4: 較正済み確率

### ストーリー 4.1: 確率がどれだけ当たるかを測る 🔵
**信頼性**: 🔵 *FR-124/§12-5*

**私は** 出力確率の信頼性を検証したい研究者 **として**
**reliability diagram と ECE で確率較正を評価し、bic と nested を別々に測ってほしい**
**そうすることで** 「確率 70% と言ったとき本当に 70% 当たるか」を backend ごとに確認できる

**関連要件**: REQ-014, REQ-015, REQ-016, REQ-017, REQ-106, EDGE-012 / **優先度**: Must Have

### ストーリー 4.2: 確率の意味の違いを明記してほしい 🔵
**信頼性**: 🔵 *FR-124*

**私は** レポートを読む第三者 **として**
**BIC 近似確率と logZ 由来確率の意味が違うことを、確率出力に backend 名付きで明記してほしい**
**そうすることで** 確率を過信せず、どの近似で得た値かを踏まえて解釈できる

**関連要件**: REQ-015, NFR-004 / **優先度**: Should Have
