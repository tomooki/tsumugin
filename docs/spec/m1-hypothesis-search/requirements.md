# m1-hypothesis-search 要件定義書

## 概要

Tsumugin マイルストーン M1: 単一パターンに対する**多仮説木探索**を実装する。
候補相集合から相組合せの探索木を構築し、ピークマッチングによる事前枝刈り・
探索モード精密化・BIC 一次評価を経て、妥当な仮説集合をランキング付きで出力する。
併せて **.gpx 書き出し保証** (FR-505) と **Web UI 最小版** (読み取り専用の結果閲覧) を提供する。

上位仕様: [docs/tsumugin_spec_v0.3.md](../../tsumugin_spec_v0.3.md) §13 M1 / FR-110〜117, FR-121/122, FR-505。
M0 実装済み資産 (RefinementBackend / StagedRefinementEngine / Evidence bic-aic / Ledger / Snapshot) の上に構築する。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 仕様書 (tsumugin_spec_v0.3.md)・M0 実装に基づく確実な要件
- 🟡 **黄信号**: 仕様書から妥当な推測で確定した要件 (推測根拠を記載)
- 🔴 **赤信号**: 仕様書にない推測による要件

### 通常要件

- REQ-001: システムは観測パターン (2θ, 強度) と候補相集合から相組合せ仮説の**探索木**を構築し、
  仮説集合をランキング付き (`RankedHypothesis`) で返さなければならない 🔵 *FR-110/P1*
- REQ-002: システムは各候補相のシミュレートピーク位置と観測ピークの**マッチングスコア**を
  計算しなければならない (ノード評価の事前指標) 🔵 *FR-111*
- REQ-003: 探索木の各ノードでは**保守的設定の制約付き精密化 (探索モード)** を実行しなければ
  ならない (scale + 格子のみ・少サイクル。段階テンプレートのフル実行は最終検証時のみ) 🔵 *FR-113*
- REQ-004: 仮説の evidence は **bic バックエンドで一次評価** し、`Hypothesis.metrics.evidence`
  に格納しなければならない (nested 裁定は M5) 🔵 *FR-121/FR-122*
- REQ-005: 探索終了時、**未マッチ観測ピーク / extra 計算ピーク**を構造化形式
  (`UnmatchedPeakReport`: 位置・強度・未知相フラグ) で出力しなければならない 🔵 *FR-117*
- REQ-006: システムは精密化済み仮説を **GSAS-II GUI で開ける .gpx ファイル**として
  書き出せなければならない 🔵 *FR-505*
- REQ-007: Web UI 最小版は解析結果 (仮説ランキング・Rwp/GOF・確率・僅差競合フラグ・
  未知相フラグ) を**読み取り専用**で表示しなければならない 🟡 *§13 M1「Web UI最小版」の
  内容を FR-421/422 の閲覧系から最小構成として推測*

### 条件付き要件

- REQ-101: 候補相のマッチングスコアが**枝刈り閾値未満**の場合、システムは当該相のノード展開を
  行ってはならない。閾値はスコア累積分布の変曲点で動的決定する 🔵 *FR-111/FR-112*
- REQ-102: 相追加による **R 改善が閾値 (既定 2%) 未満**の場合、システムはその枝の展開を
  打ち切らなければならない 🔵 *FR-115*
- REQ-103: 等構造 (ピーク位置が Jaccard 類似) の候補相が複数ある場合、システムは
  **FoM = 1/((1−fit)+ΔU) で代表を選出**し、他相を代替解 (`alternatives`) として保持
  しなければならない (削除しない) 🔵 *FR-114*
- REQ-104: 探索完了後、システムは **Jenks natural breaks** により良好解クラスタを
  抽出しなければならない 🔵 *FR-116*
- REQ-105: GSAS-II 未導入環境で .gpx 書き出しが要求された場合、システムは
  `GSASUnavailableError` を送出しなければならない 🟡 *M0 の GSASIIBackend 設計の踏襲*
- REQ-106: 全仮説が高 R 値 (閾値超) の場合、システムは**未知相フラグを強制表示**
  しなければならない 🔵 *FR-403/§14 リスク緩和*

### 状態要件

- REQ-201: `refined` 状態に達した仮説のみが最終ランキングの対象とならなければならない
  (探索途中の `candidate` はランキング外) 🟡 *§4 Hypothesis.status の意味から推測*
- REQ-202: 探索木のノード分岐時、子仮説の `parent_id` は親仮説 ID を保持しなければならない
  (系譜の追跡可能性) 🔵 *§4 Hypothesis.parent_id*

### オプション要件

- REQ-301: Web UI は仮説間の簡易比較 (メトリクス並置) を提供してもよい (フル diff は M2 FR-422) 🟡
- REQ-302: 木探索はプライマリヒストグラムのみで実行してよい (joint 検証は M4 FR-245) 🔵

### 制約要件

- REQ-401: 1 仮説の最大相数は既定 5 とし、設定可能でなければならない 🔵 *FR-115*
- REQ-402: 探索の全操作 (ノード生成・枝刈り・精密化・クラスタリング・採択) は理由付きで
  Ledger に記録され、仮説は非破壊 (追記のみ) で保存されなければならない 🔵 *P2/FR-214*
- REQ-403: 同一入力・同一設定での探索結果はビット同一でなければならない 🔵 *NFR-102*
- REQ-404: 探索ノードの評価は将来の Worker 並列化 (NFR-104) を阻害しない純関数的構成と
  しなければならない (M1 実行は逐次でよい) 🟡 *NFR-103/104 から設計配慮を導出*
- REQ-405: 枝刈り・降格はすべて理由付き記録とし、ChemPlausibility 由来の候補除外は
  行わない (同機能は M4) 🔵 *FR-412 Dara 教訓*

## 非機能要件

### パフォーマンス

- NFR-001: 探索モード精密化は 1 ノードあたり数サイクル以内の軽量設定とする
  (NFR-103 の 3 分/300 相目標への布石。M1 での実測ベンチは対象外) 🟡
- NFR-002: 候補 N 相・最大 K 相のとき、評価ノード数が組合せ爆発しないこと
  (枝刈りにより O(N·K) オーダーの精密化回数に抑制) 🟡 *FR-111 の目的から推測*

### セキュリティ

- NFR-101: Web UI / API サーバは既定で localhost バインドとする 🟡 *ローカル解析ツールとしての推測*

### 信頼性・再現性

- NFR-201: Ledger は追記専用 + ハッシュチェーンで `verify()` が常に True 🔵 *NFR-105*
- NFR-202: 乱数を使用する場合は種を固定し、結果はビット同一 🔵 *NFR-102*

## Edgeケース

### エラー処理

- EDGE-001: 候補相ゼロ → 空のランキングを返す (例外を投げない) 🔵 *M0 pipeline の規約踏襲*
- EDGE-002: 全仮説高 R 値 → 未知相フラグ + 最良仮説を「要確認」として返す 🔵 *FR-403*
- EDGE-003: 観測ピークが検出できない (フラット/ノイズのみ) → マッチングスコア全ゼロ、
  未知相フラグなしの空良好解 + 警告 🟡
- EDGE-004: 精密化が発散した探索ノード → chi2=inf として扱い、その枝を降格 (クラッシュしない) 🔵 *M0 規約*

### 境界値

- EDGE-101: 最大相数 (5) に到達した枝は展開を停止する 🔵 *FR-115*
- EDGE-102: 候補が 1 相のみ → 木は深さ 1、単一仮説のランキングを返す 🔵
- EDGE-103: 全候補が同一構造 (完全 Jaccard 重複) → 代表 1 相 + 代替解 N−1 相 🔵 *FR-114*

## M1 スコープ外 (明示)

- 相ライブラリ取り込み・重複排除・hull フィルタ (FR-100〜105) — 候補相は API 引数で受領
- マルチスタート (FR-230)、シーケンシャル (FR-300)、ChemPlausibility (FR-412)、
  nested sampling (FR-121 `nested`)、REST API / MCP (FR-512/513)、レポート PDF (FR-504)
