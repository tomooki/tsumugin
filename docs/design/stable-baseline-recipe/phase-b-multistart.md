# Phase B 設計: 初期値摂動の並列実行による収束確認

**位置づけ**: Phase A (手順最適化) で「収束する手順」を 1 つ決めたあと、**その手順を固定したまま
初期値を振って**同じ解に来るかを確かめる。手順を固定するので、観測されるベイスン構造は
**最適化問題そのものの性質**であり、手順差との交絡が無い。

**Phase A の実測が示したこと** (この設計の動機): 手順どうしの一致を傍証にすると、T3 の一致は
`{serious2, serious1}` (rounds だけが違う近重複) から来て、最良解 `sizestrain_last` は孤立した。
**手順差とベイスン差が混ざる**ため、一致しても「同じ最小点」なのか「似た手順だから似た答え」
なのか切れない。初期値摂動ならこの交絡が構造的に無い。

---

## 1. ⚠ 既存実装で成り立たない前提が 2 つある

### 1.1 `agreement` の独立性判定が**このモードでは逆を向く**

`agreement._independence` は「値がビット同一」「実効軌跡が同一」を **DUPLICATE** (証拠にならない)
と判定する。手順比較ではこれが正しい — 同じ道を歩いた 2 案の一致は情報量ゼロだから。

しかし初期値摂動では:

- 全開始点が**同じ手順**を走るので、実効軌跡 (段ラベル + 母数) は**構造的に同一**になる。
  → 現状のまま使うと全対が DUPLICATE になり、**傍証は永久に成立しない**。
- 別々の初期値から出発して**ビット同一の解**に来ることは、収束の**最強の証拠**である。
  → 現状のまま使うと最強の証拠を「情報量ゼロ」と判定する。

**対処**: 「何がこの 2 つを別の実験にしているか」はモードで違う、という事実を型に出す。

```
IndependenceBasis = "procedure" | "start"
```

- `procedure` (既定・現行): 実効軌跡が違えば独立。ビット同一は DUPLICATE。
- `start`: **初期値が違えば独立**。軌跡の同一もビット同一も DUPLICATE にしない。
  代わりに「摂動が実際に効いたか」を別に見る (下記 1.3)。

`ProcedureProvenance` に `start_key: tuple[...]` (適用した摂動) を末尾追加し、`start` モードでは
`start_key_a != start_key_b` を独立性の根拠にする。**モードを省略可能にはしない** — 既定のまま
呼ぶと Phase B が永久に非傍証になるので、`cluster_agreement_basins(..., basis=...)` を必須にする
案も検討したが、既存呼び出し (search) が壊れるため既定 `procedure` + Phase B 側が明示指定とする。

### 1.2 摂動軸が格子だけでは**構造の局所解を試験していない**

現状の唯一の軸は `initial_cell_scale` (格子 a,b,c の相対倍率)。しかし Rietveld の局所解は
**主に構造 (原子座標)** にある — 格子は擬似的に 1 次元的で、格子だけ振っても「格子のベイスンが
1 つ」しか言えない。Issue #13 が「原子座標摂動は M-later」と書いている当の欠落がここ。

| 軸 | engine のフック | 状態 |
|---|---|---|
| 格子 | `initial_cell_scale` | ✅ 実装済 |
| 占有率 | `initial_occupancies` | ✅ 実装済 (絶対値シーダー) |
| 相分率 | `_apply_initial_fractions` | ✅ 実装済 |
| **原子座標** | — | ❌ **無い (本 Phase で新設)** |

### 1.3 座標摂動は**対称性を壊してはならない**

原子を特殊位置から動かすと空間群が壊れる。したがって摂動は**対称性が自由な軸だけ**に
掛ける必要がある。WS-0 で入れた `GetCSxinel` の 3 状態 (`atomrows.free_index_from_site_symmetry`)
がそのまま使える — `0` の軸には触らず、結束軸は代表軸だけ動かす。

⚠ **摂動が「効いた」ことを確認する必要がある**。対称性で全軸が固定された構造 (高対称相) では
座標摂動が**全て無効**になり、開始点が実質 1 つになる。それを傍証と呼んではいけないので、
実際に動いた軸数を記録し、0 なら「この軸では試験していない」と報告する (`min_procedures` と
同じ「空虚な True を作らない」規律)。

## 2. 設計

### 2.1 engine: 座標シーダー `initial_coord_jitter`

```
run_auto_rietveld(..., initial_coord_jitter: Mapping[str, float] | None = None,
                       jitter_seed: int = 0)
```

- 値は**相名 → 変位の大きさ (Å)**。分率ではなく Å にするのは、`agreement` の床と同じ理由で
  分率は軸ごとに意味が変わるため (a=5Å と c=20Å で 0.01 の意味が 4 倍違う)。
- 適用対象は**対称性が自由な軸のみ**。`_phase_atom_info` が既に `GetCSxinel` を引いているので
  そこで得た自由度指標を使う。結束軸 (同じ正値) は代表軸だけ動かし、GSAS の等値拘束に従わせる。
- 決定論: `numpy.random.default_rng(jitter_seed)` で生成し、**開始点 index を種に混ぜる**。
  同じ種なら何度実行してもビット同一 (NFR-102)。
- 戻り値に**実際に動かした軸数**を載せる (§1.3)。

### 2.2 `multistart`: 開始点の生成を多軸へ

```
@dataclass(frozen=True)
class StartPerturbation:      # 1 開始点が適用する摂動 (これが start_key になる)
    cell_scale: Mapping[str, tuple[float, float, float]]
    coord_jitter_ang: float
    jitter_seed: int
    occupancy_delta: float
```

- 既定の軸は **格子 + 座標**。占有率は相が占有率グループを宣言しているときだけ
  (宣言が無い相で占有率を振っても精密化されないので無意味)。
- 生成は現行の決定論グリッド (`_grid_scales`) を踏襲し、座標は種で決める。
- **開始点 0 は無摂動** (基準)。奇数本なら現行どおり中央が 1.0 になる。

### 2.3 並列実行 — **これが「規定で回せる」根拠**

ベンチマークハーネスと**同じ 2 層方式**にする: `ProcessPoolExecutor` + 1 開始点 1 プロセス。
GSAS-II はグローバル状態を持つので同一プロセスでの連続実行は隔離が保証できない。

**`jobs` の既定は `n_starts`** (コア数で上限)。開始点は互いに独立なので、**壁時計は 1 開始点分**に
なる。N 倍にはならない。

実測 (2026-07-30 のキャンペーン。**すでに 8 並列の負荷下で測った値**なので競合込み):

| データ / 手順 | 1 開始点の壁時計 | N=5 並列の壁時計 (見込み) |
|---|---|---|
| T3 `serious1` (既定候補で最遅) | 3.7 分 | **≈ 3.7 分** |
| T3 `sizestrain_last` / `polish` | 1.3–1.5 分 | ≈ 1.5 分 |
| T1 `serious1` | 2.2 分 | ≈ 2.2 分 |
| CaTeO3 (全候補) | ≤ 1.7 分 | ≈ 1.7 分 |

同キャンペーンは CPU 合計 ~40 分の 40 セルを `--jobs 8` で**壁時計 ~10 分**に畳んでおり
(律速は最長セル 5.6 分)、この機械で並列が実効していることの直接の証拠になっている。

したがって**標準経路 (Phase A → Phase B) を丸ごと回しても壁時計は数分**である:

```
Phase A: 候補 4-5 本を並列       → 壁時計 ≈ 最遅候補 (T3 で 3.7 分)
Phase B: 開始点 5 本を並列        → 壁時計 ≈ 1 開始点 (T3 で 1.5 分)
                                   合計 ≈ 5 分 (T3) / 1-2 分 (T1/T2/CaTeO3)
```

→ **multistart は opt-in ではなく規定 (既定 ON) にする。**

⚠ **決定論のための規律 4 つ** (ハーネスで踏んだ罠と同型):

1. 結果は**完了順ではなく開始点 index 順**に並べ直す。
2. **ledger 追記は join 後に列挙順で再発行**する (`Ledger` はハッシュ鎖 / NFR-102。
   完了順の追記はビット同一性を壊す)。
3. 子の stdout を跨がせない (プロセス間は pickle で結果を返すので、ハーネスの cp932 罠は
   発生しない — ただし例外は pickle 可能な形へ落とすこと)。
4. **各ワーカーで BLAS/OpenMP のスレッド数を 1 に固定する** (`OMP_NUM_THREADS=1` 等)。
   理由は 2 つあり、後者が本質: (a) N プロセス × M スレッドの過剰購読を避ける、
   (b) **BLAS の縮約順序はスレッド数で変わり得るため、スレッド数が実行時の負荷で揺れると
   浮動小数がビット同一にならない** — NFR-102 の再現性契約が並列化で静かに壊れる経路である。

### 2.4 ベイスン判定を `agreement` へ差し替え

`_cell_key` / `_same_basin` / `cluster_rietveld_basins` を廃し
`agreement.cluster_agreement_basins(..., basis="start")` を使う。得られる違い:

| | 現行 | Phase B |
|---|---|---|
| 比較対象 | 格子 a,b,c のみ | 格子 + **座標** + 占有率 (構造クラス) |
| 許容 | 固定相対 1e-2 | **esd スケール** (k=3) + クラス毎の床 |
| クラスタ | 貪欲最初一致 (**列挙順依存**) | union-find (推移閉包・順序非依存) |
| 出力 | ベイスン数のみ | 鎖か clique か・**不一致の犯人**・最初に落ちた条件 |

現行の 3 関数は削除する (「同じベイスン」の実装が 3 つある状態を減らす)。

### 2.5 Phase A → Phase B の順序を配線

`run_auto_rietveld` は**単発プリミティブのまま変えない** (insitu が per-frame で呼ぶ。
REQ-SAR-502)。新しい薄いオーケストレータを置く:

```
autorietveld.confirm.optimize_then_confirm(
    histograms, phases, *, search=..., multistart=..., ...
) -> ConvergenceReport
```

1. `run_recipe_search` で手順を最適化 → **収束した候補**を採用 (「一つでも収束すれば採用」)
2. 採用候補の `stages` + `stability` + (適応層が変えた) `histograms` を**固定**
3. その手順で `run_multistart_rietveld` を回す
4. `ConvergenceReport` = 採用手順 + 開始点別の結果 + `agreement` のベイスン + 傍証判定

⚠ **2 の「固定」が要点**。適応候補が勝った場合はレンジも背景項数も変わっているので、
元の入力で multistart を回すと**別の土俵で収束確認したことになる**。

### 2.6 開始点数の既定

`n_starts` 既定 **5**。奇数にするのは現行の決定論グリッド (`_grid_scales`) が奇数本のとき
**中央に無摂動 (倍率 1.0) を含む**ためで、基準点が常に開始点集合に入る。5 本あれば
`min_procedures=3` (傍証に必要な比較可能数) を発散 2 本まで許容して満たせる。

### 2.7 傍証の判定

`is_globally_corroborated` = 単一ベイスン ∧ valid 開始点 ≥2 ∧ 発散 0 ∧ **実際に摂動が効いた**。
落ちた条件名を返すのは `agreement` と同じ規律 (`corroboration_reason`)。

**単一ベイスンでないことは失敗ではなく所見**である — 「この手順・このデータでは初期値依存が
ある」という報告が正しい出力で、隠したり閾値を緩めたりしない。

### 2.8 ②③ 露出

- ② `auto_rietveld` に `multistart` 引数 (JSON: `{"n_starts": 5, "lattice_frac": 0.01,
  "coord_jitter_ang": 0.05, "jobs": 5}`) を足し、返り値に `convergence` を載せる。
  引数はすべてスカラなので §4.5 の到達可能性を満たす (他ツールの出力を要しない)。
- ③ `skills/analyze` に「収束を確認する」節。**手順探索の後に回す**ことと、
  単一ベイスンでなかったときに閾値を緩めない (別の初期値を足す/報告する) ことを明記。

## 3. 検証

| 対象 | 内容 |
|---|---|
| numpy 決定論 | 開始点生成・ベイスン判定・傍証条件 (GSAS 非依存) |
| 変異実証 | `start` モードでビット同一を DUPLICATE にしない / 軌跡同一を DUPLICATE にしない / 摂動が効かない構造で傍証を主張しない / 完了順で ledger を書かない / 対称固定軸を動かさない |
| gated 実データ | **T1** を `polish` (Phase A の勝者) で N=5・±0.7% 格子 + 0.05Å 座標 → 単一ベイスンか。**T3** を `sizestrain_last` で同様 |
| 非回帰 | 既定経路の T1 が `9.80617260074067` でビット同一 (カナリア) |

**実測コスト見積り**: T1 ~30s/開始点、T3 ~78s/開始点。N=5・5 並列で T1 ≈ 1 分、T3 ≈ 1.5 分。

## 4. 未解決 / 判断が要る点

1. **座標摂動の既定の大きさ**。0.05 Å は結合距離精度 (`agreement` の床 0.02 Å) の 2.5 倍で、
   「同じ最小点なら戻ってくる」程度を意図している。大きすぎると別の相へ落ち validity で
   降格される (それはそれで所見)。実測して決めたい。
2. **T4 (多相/TOF) は引き続き範囲外**。Phase B でも多相の相分率摂動は実装するが未検証。
3. ~~`serious` 系は 1 開始点 3-6 分かかるので multistart は opt-in 想定~~ →
   **撤回 (誤り)**。これは CPU 時間の合計であって壁時計ではなかった。開始点は互いに独立で
   並列化できるので、壁時計は 1 開始点分にしかならない (§2.3 の実測)。**multistart は規定 (既定
   ON) とする。**
