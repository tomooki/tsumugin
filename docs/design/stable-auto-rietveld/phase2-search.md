## 設計が確定した根拠 (実測)

**単一レシピを既定に据える設計は棄却済み** (2026-07-28 決定ログ)。3 レシピが 3 通りの勝ち方をした:

| | M7 既定 | 本気(U,V,W 単独) | 本気(U,V,W 累積) |
|---|---|---|---|
| T1 | 9.83 | **9.69** | 10.45 |
| T3 | 6.66 | **6.02** | 6.10 |
| CaTeO3 | 12.43 | 18.07 | **12.19** |
| T4 | **~12.8** | 14.53 | 14.58 |

加えて試料変位段の配置 4 通り × 4 データでも、**どの配置でも 1 つ以上が落ちた**。
順序を当てるのは不可能であり、**測って選ぶ**しかない。

## 中核の設計判断

### S1. 選択規則は「収束したものの中で最良」— Rwp 単独ではない

```
1. 収束フィルタ  : diagnostics.is_converged() が False の候補を落とす
2. 妥当性フィルタ: check_validity が fail の候補を降格 (除外はしない — 所見付きで残す)
3. 最良選択      : 残った候補から Rwp/GOF が最良のものを採る
```

**なぜ Rwp だけで選ばないか**: `Maximum shift/esd = 258.822` を出しながら「改善した」として
通過する段が実在する (requirements.md F4 周辺の実測)。**収束していない best は最良ではない**。
相数の比較に Rwp を使わない既存の規律 (`insitu.anchor.select.frame_bic`) と同じ発想を、
レシピ選択へ適用する。

⚠ **候補間で母数 (n_params) が違う場合は Rwp 比較が不公平になる。** 本気フィットは既定より
多くのパラメータを解放しうるので、**同点近傍 (Rwp 差 < 0.1 ポイント) では BIC で裁定**する。
BIC = χ² + n_params·ln(n_obs) (`frame_bic` と同一式)。

### S2. 候補セットは「固定 + 適応」の 2 層

| 層 | 内容 | 根拠 |
|---|---|---|
| 固定 | `build_recipe` (既定) / `build_serious_recipe` (累積) | 3 データで別々に勝っている実績 |
| 適応 | WS-4 の自動判定 (レンジ・背景項数) を当てた変種 | 手動調整の穴を埋める (T4 の非収束主因はレンジ未設定) |

**適応層を固定層と別候補にする**のが要点。自動判定が外した場合に固定層が保険になる。
「自動判定を既定へ埋め込む」と外したとき逃げ道が無い。

### S3. 不一致は「警告」であって「失敗」ではない (REQ-SAR-501)

候補間で最良と次点の Rwp 差が小さい (< 0.5 ポイント) のに**格子や相分率が有意に違う**場合、
その解は**順序依存 = 信頼度が低い**。これを警告として出す。

自動解析ソフトの価値は「答えを出すこと」ではなく「**答えの信頼度を言えること**」にある。
候補を複数走らせた副産物としてこれが得られるのは、探索方式の最大の利点である。

### S4. ビームサーチは v1 では採らない

段ごとに上位 k 状態を保つビームサーチ (提案 O) は探索効率が良いが:
- gpx のコピーが段数 × k 個必要でディスク/メモリの見積りが立っていない
- 「どの段で分岐したか」の記録が複雑になり ledger の可読性が落ちる

**v1 は候補レシピの独立実行 (embarrassingly parallel) に留める。** 時間は無視できる前提なので、
探索効率より**実装の単純さと再現性**を優先する。ビームサーチは v1 の実測後に再検討。

### S5. 決定論 (P-SAR-4 / NFR-102)

- 候補の列挙順は固定 (辞書順でなく明示的なタプル)
- 並列実行しても**選択は列挙順で解決**する (完走順に依存しない)
- 同点は列挙順の先頭を採る (実行時間や浮動小数の揺らぎで結果が変わらない)

### S6. operando は探索しない (REQ-SAR-502)

`tsumugin.insitu` は既定で軽量レシピ 1 本。フレーム数 × 候補数の積は現実的でない。
**時間予算があるのは operando だけ**という前提を明示的に守る。

## モジュール構成

```
autorietveld/search.py
  ├─ RecipeCandidate      : (name, recipe, 由来)  — 候補 1 つ
  ├─ CandidateOutcome     : 候補 1 つの結果 (result + diagnostics + 採否理由)
  ├─ RecipeSearchResult   : 全候補 + 選択された候補 + 警告
  └─ run_recipe_search()  : 候補を実行し S1 の規則で選ぶ
```

- `run_auto_rietveld` は**変更しない** (候補 1 つの実行に使うだけ)
- 並列実行は呼び出し側の責務にする (ハーネスと同じ「1 件 1 プロセス」方式を再利用可能に)
- 返り値は素の dataclass → `to_dict()` で ② MCP へ載る

## ② MCP 露出 (CLAUDE.md ★不変条件)

**同じ PR で露出する。** 案:
- 既存 `auto_rietveld` に `search: bool | list[str]` を追加 (候補名の列)
- 返り値に `candidates[]` (各候補の Rwp/収束/採否) と `warnings[]` を含める

③ の手順書 (`plugins/tsumugin/skills/analyze/SKILL.md`) に「**いつ探索を使うか**」を書く:
> 単一フレームの本気解析では既定で探索を使う。operando では使わない (時間予算)。
> 候補間で答えが割れた警告が出たら、その解は順序依存なので**追加測定か手動確認**を提案する。

## 検証計画

1. 6 データすべてで、探索の選択が**各データの既知最良と一致する**こと
   (T1/T3 → 本気単独、CaTeO3 → 本気累積、T4 → 既定)
2. 決定論: 同一入力・同一 seed で 2 回走らせてビット同一
3. operando 非回帰: `insitu` 経路で探索が起動しないこと
4. 警告の実証: 意図的に僅差の候補を与えて S3 の警告が出ること
